\chapter*{Resumo executivo}
\addcontentsline{toc}{chapter}{Resumo executivo}

O OrbitBoard é uma aplicação full stack para gestão de projetos, tarefas e responsabilidades de uma equipe. O frontend foi construído com React e Vite. O backend usa ASP.NET Core 8 e expõe uma API REST documentada por Swagger. A execução integrada ocorre por Docker Compose, com Nginx servindo o frontend e health checks para os dois serviços.

A equipe adotou a aplicação base fornecida pelo docente e concentrou o desenvolvimento na revisão da arquitetura, conteinerização, configuração de CORS, atualização de dependências, documentação, validação da comunicação HTTP e organização do fluxo Git. Os dados permanecem em memória para manter o foco didático na integração entre camadas.

\begin{resumobox}[Resultado técnico atual]
  \begin{itemize}
    \item Backend compilado sem erros e sem avisos, com 29 testes automatizados aprovados.
    \item Frontend compilado com Vite 8.1.5 e 10 testes automatizados aprovados.
    \item Docker Compose validado com backend e frontend saudáveis.
    \item Swagger, frontend e endpoints de saúde acessíveis nas portas documentadas.
    \item Pipeline do GitHub Actions aprovada para backend, frontend e containers.
    \item Roteiro com quatorze evidências, todas registradas pela equipe.
  \end{itemize}
\end{resumobox}

\section{Fluxos principais}

\subsection{Cadastro de projeto}

O usuário abre a tela de projetos, preenche nome, descrição, status, datas e responsável. O frontend serializa o formulário em JSON e envia uma requisição \texttt{POST}. A API valida os dados, aplica regras de unicidade e devolve \texttt{201 Created}. O frontend então recarrega a listagem e apresenta uma mensagem de sucesso.

\subsection{Cadastro e movimentação de tarefa}

A tarefa é criada para um projeto existente. O usuário informa título, descrição, prioridade, responsável, prazo e estimativa. Depois da criação, a tarefa aparece no quadro. A mudança de coluna envia uma requisição \texttt{PATCH} contendo apenas o novo status.

\subsection{Tratamento de conflito}

Ao tentar criar um projeto com nome já existente ou excluir um projeto que ainda possui tarefas, a API responde com código \texttt{409}. O middleware padroniza a resposta e o frontend apresenta a mensagem sem perder o estado da tela.

\section{Fluxo HTTP e JSON}

\begin{enumerate}
  \item O usuário executa uma ação na interface.
  \item O cliente em \texttt{frontend/src/api/client.js} cria a requisição.
  \item A URL base é obtida de \texttt{VITE\_API\_URL}.
  \item O controller recebe o JSON e o ASP.NET Core valida o DTO.
  \item O serviço aplica a regra de negócio e atualiza as coleções em memória.
  \item A API devolve JSON, resposta sem conteúdo ou \texttt{ProblemDetails}.
  \item O frontend atualiza a tela ou apresenta a mensagem correspondente.
\end{enumerate}

\section{CORS}

O navegador abre o frontend em \url{http://localhost:5173} e acessa a API em \url{http://localhost:5200}. Como as origens são diferentes, a API usa a política \texttt{Frontend}. A lista de origens é lida da seção \path{Cors:AllowedOrigins}. No Compose, a variável \path{CORS_ALLOWED_ORIGIN} preenche \path{Cors__AllowedOrigins__0}.

\section{Persistência em memória}

O serviço usa listas protegidas por bloqueio de sincronização. Essa implementação é suficiente para o protótipo acadêmico, reduz a configuração inicial e permite demonstrar todas as operações HTTP. A limitação principal é a perda dos dados quando a API reinicia.

\chapter{Backend e contrato da API}

\section{Organização interna}

Os controllers expõem endpoints HTTP e delegam operações ao \texttt{IWorkspaceService}. Os DTOs definem contratos de entrada e saída. As entidades e enums ficam em \texttt{Models}. O middleware captura exceções e devolve \texttt{ProblemDetails}. O serviço singleton mantém os dados iniciais e aplica as regras de negócio.

\chapter{Integração contínua e fluxo Git}

\section{Pipeline}

A pipeline é executada em pushes e MRs destinados a \texttt{develop} e \texttt{main}. Ela possui três jobs:

\begin{enumerate}
  \item \textbf{Build backend}: restaura pacotes e compila a solução em modo Release.
  \item \textbf{Build frontend}: instala dependências com \texttt{npm ci} e executa o build.
  \item \textbf{Build containers}: valida o Compose e compila as duas imagens.
\end{enumerate}

O job de containers depende da aprovação dos builds das aplicações. Isso impede a criação das imagens quando alguma camada não compila.

\chapter{Limitações, riscos e próximos passos}

\section{Limitações conhecidas}

\begin{itemize}
  \item Os dados são apagados quando a API reinicia.
  \item Não existe autenticação ou autorização.
  \item A URL da API é incorporada ao frontend durante o build.
  \item O estado em memória não permite escalar o backend horizontalmente.
  \item A aplicação foi projetada para uso didático e execução local.
\end{itemize}

\end{itemize}

\chapter{Conclusão}

O OrbitBoard demonstra os elementos centrais de uma aplicação full stack: interface web, API REST, comunicação HTTP e JSON, validação, tratamento de erros, CORS, documentação OpenAPI e execução conteinerizada. A infraestrutura criada permite reproduzir o ambiente com poucos comandos e a pipeline reduz o risco de integrar alterações que não compilam. Testes automatizados de backend e frontend cobrem as regras de negócio e os fluxos principais da interface.

A documentação registra a arquitetura, as decisões, os contratos, os ajustes, o processo de trabalho e a contribuição real de cada integrante. O Makefile facilita a execução por todos os integrantes. As quatorze evidências planejadas estão registradas, o que torna a preparação final objetiva.

O estágio técnico está avançado. A conclusão depende principalmente da execução do roteiro de testes manuais pela equipe, do ensaio da apresentação e da integração final por MR.
